# Templating

Flare's content elements render Twig templates. A Flare `Engine` object is made availble as `flare` variable in those
templates to interface with the list or reader in the current context.

:::tip
Use the bundled templates as your starting point. They reflect the current runtime API.
:::

## Quick Start

:::info
**When upgrading to Flare v0.1**&ensp;&ndash;&ensp;Older Flare documentation referred to Twig helpers such as `flare_form(...)`, `flare_make_list(...)`,
and direct access to `flare.entries`. These functions and accessors are no longer available.
:::

- `flare` is the engine injected by the content element controller
- `flare.createView` creates the runtime view object for the current context
  ```twig
  {% set flare_view = flare.createView %}
  ```
- Reader templates work with a `ValidationView`
- List templates work with an `InteractiveView`<br />
  Within an `InteractiveView`:
    - Create the list view:
      ```twig
      {% set flare_list = flare.createView %}
      ```
    - Create the Symfony Form views for filtering:
      ```twig
      {% set form = flare_list.form.createView %}
      ```
    - Access entries:
      ```twig
      {% for entry in flare_list.entries %}
        <h3>{{ entry.headline }}</h3>
      {% endfor %}
      ```
    - Display a paginator:
      ```twig
      {{ include('@Contao/flare/paginator.html.twig', { paginator: flare_list.paginator }) }}
      ```

## Template Locations

### Bundled Templates

The bundled templates live in:

```text
vendor/heimrichhannot/contao-flare-bundle/contao/templates/
```

The main content element templates are:

```text
vendor/heimrichhannot/contao-flare-bundle/contao/templates/content_element/flare_listview.html.twig
vendor/heimrichhannot/contao-flare-bundle/contao/templates/content_element/flare_reader.html.twig
```

Related partials live in:

```text
vendor/heimrichhannot/contao-flare-bundle/contao/templates/flare/
```

### Custom Templates

To override or extend the provided templates, create Twig files in a Twig template directory of your Contao
installation. Assuming there is a `.twig-root` file in `contao/templates/`, a typical structure looks like this:

```text
contao/templates/content_element/{flare_listview,flare_reader}/my_variant.html.twig
```

You can then select the variant via the content element's `customTpl` field.

## List View Templating

The default list template creates an interactive view first and then renders the filter form, entries, and paginator
from that view.

```twig title="contao/templates/content_element/flare_listview/my_variant.html.twig"
{% extends "@Contao/content_element/flare_listview.html.twig" %}

{% set flare_list = flare.createView %}

{% block filter %}
    {% set form = flare_list.form.createView %}

    {{ form_start(form) }}
        {{ form_widget(form) }}
        <button type="submit">{{ 'submit'|trans({}, 'flare_form') }}</button>
    {{ form_end(form) }}
{% endblock %}

{% block list %}
    {% for entry in flare_list.entries %}
        <article>
            <h3>
                {% if entry.to %}
                    <a href="{{ entry.to }}">{{ entry.headline ?? entry.title ?? '' }}</a>
                {% else %}
                    {{ entry.headline ?? entry.title ?? '' }}
                {% endif %}
            </h3>
        </article>
    {% else %}
        <p>No entries found.</p>
    {% endfor %}
{% endblock %}

{% block pagination %}
    {{ include('@Contao/flare/paginator.html.twig', {
        paginator: flare_list.paginator
    }) }}
{% endblock %}
```

### Available Variables in List Templates

The list content element injects these template variables:

- `flare`: the `Engine`
- `content_model`: the `tl_content` model of the current content element
- `headline`: the normalized Contao headline data

After creating the view with `flare.createView`, you typically work with:

- `flare_list.form`: the Symfony form object
- `flare_list.entries`: the entries of the current page (see [Entries](#entries))
- `flare_list.paginator`: the paginator
- `flare_list.count`: the total result count (for the pagination); `flare_list.entries|length` is the page's count
- `flare_list.failed`: whether the list could not be created (see [Block Structure](#list-template))

### Entries

`flare_list.entries` is a collection of entries — one `Entry` per row of the current page, in order. It is loaded on
first access. `is empty`, `|length` and `loop.last` work on it, and you can loop over it as often as you like.

An entry gives you the row's columns by name: `entry.headline` is the `headline` column. A column whose value is
`null` is no error, also not in debug mode. Values that [event listeners](dev/entries.md) attach to the entries
(e.g. `entry.archive`) read the same way.

Three names are reserved and never read from the row:

| Name | Value |
|---|---|
| `entry.to` | The reader URL of the entry, or `null` — without a configured reader page, or when the entry's auto-item value is empty. |
| `entry.row` | The row as an array: `entry.row.<column>`. Use it for a column named `to`, `row` or `meta`, and to iterate the columns — an entry itself is not iterable. |
| `entry.meta` | Metadata. `entry.meta.modelRef.table` and `entry.meta.modelRef.id` name the database record of the entry (`entry.meta.modelRef` is `null` for entries that do not come from a table). |

```twig
{% if flare_list.entries is empty %}
    <p>No entries found.</p>
{% else %}
    <p>{{ flare_list.entries|length }} of {{ flare_list.count }} entries</p>
{% endif %}

{% for entry in flare_list.entries %}
    <article>
        <h3><a href="{{ entry.to }}">{{ entry.headline }}</a></h3>
        {# a news list: the title of the entry's archive #}
        <p>{{ flare_related(entry, 'pid').title }}</p>
        <dl>
            {% for column, value in entry.row %}
                <dt>{{ column }}</dt><dd>{{ value }}</dd>
            {% endfor %}
        </dl>
    </article>
    {% if not loop.last %}<hr>{% endif %}
{% endfor %}
```

In a list loop, `flare_related()` costs one query per distinct related record (N+1). A
[listener that attaches the related records in phase 1](dev/entries.md#2-a-related-record-to-one) loads them for the
whole collection in one query.

A name that is neither a column nor an attachment follows Twig's rules: it renders nothing, or raises a Twig error in
debug mode (`strict_variables`). Use `entry.subtitle ?? ''` or `entry.subtitle is defined` for columns that not every
row has.

:::note[No models in templates]
Entries replace the Contao models that list and reader templates received before (see
[Removed in v0.2](removed-in-v0.2.md#twig)). Related records come from [`flare_related()`](#twig-helpers), content
elements from `flare_content(entry)`, anything else from an [entries listener](dev/entries.md).
:::

### Customizing the Filter Form

The filter form is a normal Symfony form. Create the form view from `flare_list.form` and apply form themes as usual.

```twig
{# assuming {% set flare_list = flare.createView %} has been defined #}
{% set form = flare_list.form.createView %}
```

You can access individual form fields by their field name. That field name is also used for the submitted query
parameter. For example, if a field is named `search`, you can access it as `form.search`:

```twig
{% set search_field = form.search %}
{{ form_row(search_field) }}
```

```twig
{% block filter %}
    {% set flare_list = flare.createView %}
    {% set form = flare_list.form.createView %}

    {% form_theme form with [
        'bootstrap_5_layout.html.twig',
        'form/my_symfony_form_theme.html.twig',
    ] %}

    {{ form_start(form) }}

        {% set search_field = form.search %}

        <div class="my-form-fields">
            <div class="my-custom-search-field">
                {{ form_row(search_field) }}
            </div>
            {{ form_rest(form) }}
        </div>

        {% block submit %}
            <button type="submit">Apply filter</button>
        {% endblock %}

        {% block reset %}
            <button type="reset" class="visually-hidden-focusable">Reset filter</button>
        {% endblock %}

    {{ form_end(form) }}
{% endblock %}
```

:::info
Because form themes are standard Symfony form themes, place them in `templates/form/` relative to the project root, not
in the Contao templates directory.
:::

## Reader Templating

The reader content element renders a single entry. Its default template extends the same base template as the list
view, but works with reader-specific variables.

```twig title="contao/templates/content_element/flare_reader/my_variant.html.twig"
{% extends "@Contao/content_element/flare_reader.html.twig" %}

{% block content %}
    <article>
        <h1>{{ entry.headline ?? entry.title ?? '' }}</h1>

        {% if entry.teaser ?? false %}
            <div>
                {{ entry.teaser|raw }}
            </div>
        {% endif %}

        {{ flare_content(entry) }}
    </article>
{% endblock %}
```

### Available Variables in Reader Templates

The reader content element injects these variables:

- `flare`: the `Engine`
- `flare_reader`: the pre-defined `ValidationView` created from `flare`
- `entry`: the `Entry` of the current reader item, read like an entry in a list (see [Entries](#entries));
  `entry.to` is its canonical reader URL
- `content_model`: the `tl_content` model of the current content element
- `headline`: the normalized Contao headline data
- `comments`: optional comments data when the comments integration attaches it

The reader template can also link to other entries of the same list with
[`flare_reader.lookup()`](#linking-other-entries). `flare_reader.backLink` exposes the link back to the configured
list view page (see [Back-to-List Button](#back-to-list-button)).

:::note
Within a reader template, creating a separate view with `flare.createView` is typically not necessary.
Instead of a `flare_list` variable, you can use `flare_reader` directly.

In a `ValidationView`, no Symfony form is available for filtering, meaning you _cannot_ use `flare_reader.form` or
similar.
:::

### Linking Other Entries

`flare_reader.lookup()` returns other entries of the list by id — e.g. editorially linked entries:

```twig
{% for linked in flare_reader.lookup([12, 15, 18]) %}
    <a href="{{ linked.to }}">{{ linked.headline }}</a>
{% endfor %}

{% set related = flare_reader.lookup(entry.related_id) %}
{% if related %}<a href="{{ related.to }}">{{ related.headline }}</a>{% endif %}
```

- **One id** returns the entry or `null`; **a list of ids** returns a collection of the found entries in the given
  order (duplicates count once). An empty list returns an empty collection without a query. An empty field (`null`,
  `''` or `0`) counts as no id: alone it returns `null`, in a list it is skipped — no guard needed.
- **Membership in this list.** Only entries of *this* list are returned, by the reader's rules: the list's filters
  with their fixed values, never the submitted form values. A linked entry is therefore shown by the reader on the
  jump-to page only if that reader uses the same list.
- **Ids only.** Pass ids of the list's own table (the `id` column) as positive numbers or their strings — not the id of a
  parent record (`entry.pid` of a news entry is an archive id: use [`flare_related()`](#twig-helpers)). Anything
  else throws an error, including the serialized array a picker field stores: deserialize it first (in PHP with
  `StringUtil::deserialize()`, in Twig with Contao's `deserialize` filter where your Contao version provides it).
- **Entries like any other.** The results have `.to` and the values [listeners](dev/entries.md) attach.
  `flare_reader.lookup(entry.id)` returns a different object than `entry`. Repeating a lookup with the same ids on
  the same view runs no second query.
- **Cache tags.** Each found entry tags the response (`contao.db.<table>.<id>`), so the page is invalidated when a
  linked entry changes.

### Reader URLs

`entry.to` is the entry's reader URL: the reader page with the entry's value of the list's auto-item field. The URL
carries the value as text (Contao's input encoding of the stored value reverted), percent-encoded once by the router,
and leads the reader back to the same entry — also for values with spaces, Unicode, quotes, `#`, `%` and `&`.

:::caution[Known limits]
An auto-item value that contains `/` or a literal `%2F` cannot make the round trip: Symfony's router keeps `%2F` as a
path separator, and Contao splits the URL parameters at `/`. On Contao 4.13, neither can a `%` followed by a letter
that `sprintf()` interprets (`%s`, `%d`, `%b`, …), which Contao 4.13's legacy URL handling decodes. Such a link ends in
a 404, never in another entry — keep these characters out of aliases.
:::

### Breadcrumb

On a reader page, the last item of Contao's breadcrumb shows the entry's page title — the same title as the page's
`<title>` (both come from the `ReaderPageMetaEvent`, see [Events](dev/events.md#readerpagemetaevent)). The breadcrumb
finds the reader by itself: the page must contain exactly one visible **Detail reader** element at the top level of
its visible articles. With none or several, without an auto-item, when no entry matches or when the list fails, the
breadcrumb stays unchanged.

:::note
The breadcrumb does not honor Contao's preview mode: a reader element or article that is visible only in the preview
is not found there.
:::

### Back-to-List Button

Reader templates can render a back-to-list button that returns visitors to the list view **with their filter and
pagination state intact**. The default reader template includes it like this:

```twig
{{ include('@Contao/flare/back_button.html.twig', { back_link: flare_reader.backLink }, with_context = false) }}
```

`flare_reader.backLink` points to the configured list view page — the list configuration's **Default List View Page**
or the reader content element's **Override Back to List View Page** (the element override wins). See
[Content Elements](content-elements.md#linking-between-list-and-reader) for the configuration side.
Without a configured page (and without `allow_any_referrer`), the component renders nothing.

#### How It Works

The component renders a regular link to the configured list view page. The FLARE frontend script then upgrades that
link in the browser:

1. When the reader was opened **from the list view** (the referrer's path matches the configured page), the link is
   replaced with the full referrer URL, so the list view's filter and pagination query parameters are preserved.
   The qualifying list view URL is also remembered per browser tab (`sessionStorage`).
2. When the visitor navigates **from one reader page to another** — e.g. via "similar entries" links generated with
   `flare_reader.lookup(id).to ?? null` (`null` for an id outside the list) — the referrer no longer qualifies, and
   the remembered list view URL is restored instead, keeping the original filter and pagination state.
3. Without JavaScript or `sessionStorage`, the link simply points to the configured list view page.

:::note
The referrer is evaluated in the browser, so the back button is fully compatible with the Contao page cache: the
cached reader HTML is identical for all visitors. Under a restrictive `Referrer-Policy` (e.g. `origin` or
`no-referrer`), the button gracefully degrades to the configured fallback URL. The browser default
(`strict-origin-when-cross-origin`) sends full same-origin referrers, so no configuration is needed.
:::

#### Variables

| Variable | Type | Description |
|---|---|---|
| `back_link` | `?BackLink` | Pass `flare_reader.backLink`. |
| `url` | `string` | Explicit fallback URL (wins over `back_link`). |
| `label` | `string` | Button text, defaults to a translated "Back to list". |
| `aria_label` | `string` | Link `aria-label`; defaults to `label` if set, a translated "Back to list" otherwise. |
| `allow_any_referrer` | `bool` | Accept any same-origin referrer, not just the configured list view page. The button then also works without a configured page and stays hidden until the script upgrades it. |
| `base_class` | `string` | Base CSS classes on the anchor (default `flare_back-button`). |
| `link_class` | `string` | Extra CSS classes on the anchor. |
| `hide_without_url` | `bool` | Hide the anchor while no URL is available (default `true`); set to `false` to keep it visible, e.g. styled as disabled. |
| `no_url_class` | `string` | CSS classes applied while no URL is available; the frontend script removes them when it upgrades the link. |

#### Bootstrap 5 Variant

`@Contao/flare/back_button/bs5.html.twig` extends the base component and only swaps the styling: `btnClass`
(default `btn btn-outline-secondary`) replaces `base_class`, and `no_url_class` defaults to Bootstrap's `disabled`
class. For example, to render the button visible-but-disabled instead of hidden while no URL is available:

```twig
{{ include('@Contao/flare/back_button/bs5.html.twig', {
    back_link: flare_reader.backLink,
    hide_without_url: false,
}, with_context = false) }}
```

## Block Structure

These are the main blocks available for extension.

### Base Template

`@Contao/flare/_flare_base.html.twig` defines:

- `wrapper`
- `headline`
- `content`
- `footer`

### List Template

`@Contao/content_element/flare_listview.html.twig` adds:

- `content_start`
- `filter`
- `body` — renders `failure` for a list that could not be created (`flare_list.failed`), `list` otherwise
  - `failure` — the translated `list.failed` message
  - `list`
- `pagination_wrapper` — renders `pagination` only for a list that did not fail
  - `pagination`
- `content_end`

Overriding `list` or `pagination` therefore never renders entries or a paginator for a failed list; override
`failure` to change the failure message, or `body` / `pagination_wrapper` to take over the whole decision.

### Reader Template

`@Contao/content_element/flare_reader.html.twig` mainly customizes:

- `content`
- `footer`

## Modding the Flare Engine

Influencing list filtering or filter form rendering is possible by adding mods to the `flare` engine before creating
the view.

```twig
{% do flare.addMod(mod_type, mod_options) %}
```

The options dictionary may be omitted for mods that don't define any options: `flare.addMod(mod_type)`.
(Both built-in mods have required options, so they are always called with a dictionary.)

For example, add filters dynamically or change the paginator url query parameter.

```twig
{%
    set modded_view = flare
        .addMod('equation', { ... })
        .addMod('page_param', { ... })
        .createView()
%}
```

If you want to create multiple views consecutively with different mods, use `flare.clearMods()` to clear the current
mod stack and start fresh.

See the [Developers / Engine Mods](dev/engine-mods) page to learn more about mods and how to create custom ones.

### Bundled Mods

Currently, only the following few mods are built-in.

#### Filter: Simple equation

Useful for showing multiple lists of different archives or categories on the same page. Just use one list view content
element and display the different lists with different mods.

- **Mod type:** `equation`
- **Mod options:**
    - `operand1` (string): the database column name to filter on,
    - `operator` (string): the operator, e.g. `=`, `>=`, `LIKE`, etc.,
    - `operand2`: the second operand, e.g., a string to match, a number to compare, an ID, etc.

#### Paginator: Page parameter

To add individual paginators to multiple lists created in one template, use this mod to change the query parameter
used for pagination.

- **Mod type:** `page_param`
- **Mod options:**
    - `param` (string): the query parameter name.

Mods are also the way to add ad-hoc filters from Twig — the built-in `equation` mod covers simple
conditions, and [custom mods](dev/engine-mods) can add any [`FilterCompound`](spec/filtering.md#1-the-filtercompound-value-object)
to the list.

### Examples

```twig
{# @var \HeimrichHannot\FlareBundle\Engine\Engine flare #}
{% extends '@Contao/content_element/flare_listview.html.twig' %}

{# @var \HeimrichHannot\FlareBundle\Engine\View\InteractiveView flare_list #}
{% set flare_list = flare.createView %}
{% set form = flare_list.form.createView %}

{% macro render_list(list_view, headline) %}
    <article class="flare-listview content-flare-listview block">
        <h2>{{ headline }}</h2>
        {% for entry in list_view.entries %}
            {# Render the entry here #}
        {% endfor %}
        <footer>
            {{ include('@Contao/flare/paginator.html.twig', { paginator: list_view.paginator }) }}
        </footer>
    </article>
{% endmacro %}

{% block list %}

    {% set list_view = flare
        .addMod('equation', { operand1: 'medium', operator: '=', operand2: 'video' })
        .addMod('page_param', { param: 'video_page' })
        .createView()
    %}
    {{ _self.render_list(list_view, 'Videos') }}

    {% set list_view = flare
        .clearMods()
        .addMod('equation', { operand1: 'medium', operator: '=', operand2: 'podcast' })
        .addMod('page_param', { param: 'podcast_page' })
        .createView()
    %}
    {{ _self.render_list(list_view, 'Podcasts') }}

{% endblock %}
```

### Debugging

We are working on improving ways to explore and document the available options per mod.

Providing an empty or malconfigured config dictionary will typically raise an exception informing you
on required and available option keys.

```twig
{% do flare.addMod('equation', { what: 'ever' }).createView %}
```

Resulting in an exception like this:

<pre style={{ whiteSpace: 'wrap' }}>An exception has been thrown during the rendering of a template
    ("The option "what" does not exist. Defined options are: "name", "operand1", "operand2", "operator".")</pre>
:::

## Twig Helpers

Flare currently registers these Twig functions (see the [Twig functions reference](reference/twig.md)):

- `flare_content(entry)` for rendering the published content elements of the entry's record (`ptable` and `pid` taken
  from `entry.meta.modelRef`). An entry without `entry.meta.modelRef` throws an error.
- `flare_enclosure(entry|array, string field = "enclosure")` for retrieving file enclosure data as you would with
  ```php
  \Contao\Controller::addEnclosuresToTemplate(...)
  ```
  For an entry, it reads `entry.row`.
- `flare_project(list, intent)` for running a projection directly from a template: returns the view
  for the given `ListCompound` and intent, without going through a content element's engine.
- `flare_related(entry, column)` for the record a column refers to, by the relation the table's DCA defines
  (`foreignKey` + `relation`), with the same result as Contao's `Model::getRelated()`: a model for a to-one relation,
  a model collection for a to-many relation, or `null`. Example: `flare_related(entry, 'pid').title` is the title of a
  news entry's archive. It returns the raw relation, without a membership check — also into the list's own table;
  when you need membership in the list or a reader link, use `flare_reader.lookup()` in a reader template; in a list,
  use the lookup a [listener's phase 1](dev/entries.md#4-computed-similarity) receives. It throws an error for an
  entry without `entry.meta.modelRef`, for a column without a relation and for a table without a model class.
- `flare_schema_org(entry = null, list = null)` returns the schema.org (JSON-LD) data of an entry. In a reader
  template, without arguments, it uses the reader's `entry` and the list of `flare`; elsewhere pass both
  (`flare_schema_org(entry, flare.list)`). The data can be influenced using the `ReaderSchemaOrgEvent`.

In reader templates, the view adds:

- `flare_reader.lookup(id)` / `flare_reader.lookup([ids])` for other entries of the list — membership in *this* list,
  so the reader on the jump-to page must use the same list; ids only, deserialize stored lists first. See
  [Linking Other Entries](#linking-other-entries).

## Comments Integration

Comments are not universally available. They are attached by Flare's comments integration when the current list and
reader setup supports them.

The default reader template renders comments in its `footer` block if comments data is present:

```twig
{% block footer %}
    {% if comments|default(false) %}
        {{ include('@Contao/flare/comments/basic.html.twig', comments) }}
    {% endif %}
{% endblock %}
```
